## Decisions needed now

### R1. The W2 console scripts fetch the kit, the binary and each host's token over plain HTTP

**Decided 2026-11-06:** keep the roughly 70-character console line (no pin). The controller alerts when a bundled host never connects within the enrollment window or its enrollment is refused; the agent reports its own binary sha256 in `hello` and the controller raises an alert-class event on a mismatch with the hash of the binary it served; bundles are served only during enrollment and each `<host>.json` is removed once that host connects. Residual risk (a trojan that lies about its own hash) accepted and written in Risks. Plan: W2 Task 3a; W12 note updated; design Enrollment, Risks, T85.

Source: owner item; `tools/invitational/e.sh`, `e.ps1` (they use `curl` and `Invoke-WebRequest` against `http://<controller>:8000`); design Enrollment ("a controller key pin and a download hash" in the one-liner); `docs/impl/12-enrollment.md` architecture note ("`tools/invitational/e.sh` and `e.ps1` stay as W2 wrote them ... the console scripts do not change").

Problem. `python3 -m http.server` serves `kit.tgz`, `phylax[.exe]` and every `<host>.json`. The bundle carries the one-time enrollment token. Anyone on the segment can (a) read a host's bundle and enroll a fake agent as that host before the real one does, which poisons the data the Invitational exists to collect, or (b) answer in the middle and swap the binary, which runs as root or SYSTEM on every host. Adding a pin or hash inside `e.sh` does not close (b) by itself: `e.sh` is itself fetched and piped to `sh`, so whoever can swap the binary can swap the script. The typed line is capped at about 70 characters of `a-z 0-9 . : / | -` (W2 Review Focus), so the pin (base64 with `+/=`) and a full hash cannot be typed. W12's pinned one-liner is 130 and 330 characters and is the production path, not a W2 option.

Options.
1. Accept for the Invitational (observe mode only), with no change.
2. Cheap mitigations in W2, no pin: the scripts print the first 12 hex characters of the sha256 of the downloaded `phylax` binary and kit, and `serve -bundles` prints the same values on the controller console, so the person at the console compares by eye (nothing is typed). Serve only during the enrollment window and stop the server afterwards. Remove each `<host>.json` from the served directory once that host shows connected. Use a short bundle TTL (the `-bundle-ttl` flag exists).
3. Add a pin and hash to `e.sh` and `e.ps1` now.
4. Serve bundles from the controller's bootstrap handler early (W12 Task 4 pulled forward).

Recommended: option 2. It costs a few lines in `e.sh`, `e.ps1`, `serve.go` output and the runbook, and it detects a swapped binary or kit, which is the serious case, without needing a typeable pin. A stolen token is already visible: the real host's enrollment is refused (`enroll.refused`) and the console shows it. Options 3 and 4 do not fit the 70-character line and duplicate W12 Task 4. Residual risk after option 2: a swapped `e.sh` can lie about the hash; this is acceptable for observe mode if the segment is not shared with red during setup. If the segment is shared, say so in the runbook and have the person read the hash from the controller, not from the script output. If option 2 is chosen, update the W12 note that says the console scripts do not change.

### R2. How a tier is switched per host: `act_enabled`, `safe_mode`, and `detect`'s own switch

**Decided 2026-11-06:** option (a). `overrides.yml` gets `act` and `safe_mode_hosts`; the `safe_mode` control request takes an optional host set; `respond.act_enabled` is the single master for tier 0 and `detect` no longer gates on its own flag; `rule_modes` stays per rule. Text and W1 schema now (Task 11b); the rendered `act:` block is W4. Design Configuration, Safe mode, `detect`, T86.

Sections: Configuration, Operations (The Invitational), Wire protocol (`safe_mode`), Module catalogue `detect` and the automatic set. Quotes: "Event-specific values are entered in the UI and written to `overrides.yml`, never to the module's base block"; "Moving to a Tier B or Tier C action is a signed config change that flips `act_enabled` for the named modules and hosts, followed by turning safe mode off for them"; the `safe_mode` message has the field `on` only; "sends a signed `control: safe_mode` to every agent".

Problem. `act_enabled` lives in `modules/<name>.yml`, which is frozen with the repo; a host's `modules:` entry overrides only `enabled`. Nothing lets `overrides.yml` carry `act_enabled`, per host or label, and the `safe_mode` control has no host set. The tiers need both (Tier B is one canary host, Tier C one scored server). Separately, `detect` forces `mode: alert` on every alert while its `act_enabled` is false, and `respond` acts only on `mode: act` alerts, but `detect` is not in the automatic set (design lines for "Generic `enabled` and `act_enabled`"), so tier 0 cannot act even when `respond.act_enabled` is true.

Options. (a) `overrides.yml` carries `act: { <module>: [<label expression>] }` and `safe_mode_hosts`, rendered into the signed config (new version per change), edited on Settings; `safe_mode` takes an optional host set (the code already works per host). `detect` stops gating on its own flag and `respond.act_enabled` is the only master; `rule_modes` stays the per-rule promotion. (b) Keep fleet-wide switches and run the tiers by separate config files. (c) Leave the text and handle tiers by hand.

Recommended: (a), written into Configuration and the control table now, because W1 defines the `ControlMsg` fields and the overrides schema. Nothing to build for the event itself: W2 Tier B uses operator-approved plans and the existing per-host `SetSafeMode`. Implementation of the rendered `act:` block can wait for the workstream that touches `respond` (W4).

### R3. Observe mode (safe mode on) cannot run the Tier A applies, and T70 forbids them

**Decided 2026-11-06:** neither option as worded. T70 lists three exceptions: the agent, the `decoys` module's listeners and the honeytoken files it plants. Tier A has decoys and honeytokens on (owner decision 2026-10-31), let through safe mode by a named allowlist; firewall shadow mode is offline only (`phylax manifest render <host> --format nft`) at the Invitational.

Sections: Operations (observe mode, Tier A), Execution engine (Safe mode), Test matrix T70. Quotes: "It suspends tier-0 responses and any running plan applies"; "safe mode is on at start"; Tier A lists "decoys, honeytokens, firewall shadow mode ... service doctor"; T70: "host state before and after a full run is identical apart from the agent".

Problem. Decoy listeners, `file.plant` honeytokens and `fw.apply mode: shadow` are plan applies; with safe mode on they never run, and if exempted, T70 is false because they change files, listeners and the firewall. W2 already resolved this for the event: the observe manifest has no decoys or canary probes, and safe mode permits read-only actions only (W2 Task on `Env.Execute`). The design text still lists them under Tier A.

Options. (a) Define Tier A as "safe mode on plus a named allowlist of apply classes that still run (shadow firewall, decoys, honeytokens, as-found backups)" and list the same exceptions in T70. (b) State that at the Invitational Tier A is read-only, decoys, honeytokens and shadow firewall move to the first full run, and keep T70 as written.

Recommended: (b). It matches what W2 builds and keeps T70 true and cheap. The decoy and shadow-firewall batteries are then tested in the lab, as the other modules are.

### R4. T+0 hand rotation covers "service accounts" with no scoring-safety net

**Decided 2026-11-06:** T+0 rotates every default password of the interactive admin identities (sysadmin, root, local Administrator, domain admins, Palo admin, VyOS vyos) and does the urgent hardening (Zerologon first). Service and application accounts are not touched at T+0; they rotate later by probed plan. Owner: "i don't want to take scored services down so just have the plan be to rotate all the default passwords and do any immediate hardening required like zerologon". Goal 1, the T+0 sheet, Operations Tier B and the Risks row reworded.

Sections: Goals (1), Enrollment (The T+0 console phase), `creds` (Rotation of unscored accounts after enrollment). Quotes: Goal 1 "Rotate admin and service credentials ... causing no failed scorer round"; T+0 sheet "Every host's `sysadmin`, root and local Administrator, the domain admins and service accounts"; `creds`: "Service and app accounts (database rows, application admin accounts) rotate by plan. Each rotation updates the files that embed the credential in the same plan, then runs the scorer-mimic probe."

Problem. At T+0 Phylax is not running, so there is no lint, probe or rollback. A service account (MSSQL logon, Splunk, the DB user in OpenCart config) changed by hand without updating the files that embed it takes a scored service down. The design also describes "service accounts" two ways (OS logon accounts at T+0, application accounts after enrollment). Tier B at the Invitational includes "T+0 admin rotation".

Options. (a) T+0 covers interactive admin identities only (local admin, root, `sysadmin`, domain admins, Palo, VyOS); every service and application account moves to the probed post-enrollment plan. (b) Keep both, with a per-service "embedded in" list on the sheet.

Recommended: (a). Reword Goal 1, the T+0 sheet generator (`phylax creds sheet`) and the Invitational Tier B description. This is the "provably safe" rule.

### R5. "Plain eviction" for service accounts can kill a running scored service

**Decided 2026-11-06:** option (a). Eviction never ends a session that owns a process of a manifest service and ends only interactive logon types (RDP, SSH, network, console). Stated in Session eviction and the `session.terminate_predating` action text; W7 policy and tests updated.

Section: Execution engine (Session eviction). Quote: "**Admin and service accounts:** plain eviction of every session that began before the rotation." Same wording in the T+0 row of Operations ("Admin and service accounts: plain eviction").

Problem. A Windows service running as the rotated account, or a long-lived DB connection it owns, has a logon session older than the rotation. `session.terminate_predating` would end it. The scored-account protections (outlived round delay, not scorer-labelled) are not applied to service accounts. Eviction is automatic under A-AUTO, and W2 Tier B performs real eviction.

Options. (a) Eviction skips any session that owns a process of a manifest service (`process.unit` or `binaries`) and is limited to interactive logon types (RDP, SSH, network, console); the rule is stated in the action contract. (b) Only (a)'s first half. (c) Leave as is and rely on R4 removing service accounts from T+0.

Recommended: (a). R4 narrows the exposure but does not remove it, since post-enrollment rotations also evict.

### R6. A work window or plan tag exempts every event on the host

**Decided 2026-11-06:** option (a), with the owner's acceptance criterion: "all red activity is seen and some blue can be shown as red, not the other way around" (Success metrics, test T82). Plan tags only on events from the step's own process tree (W1 Task 32a); work-window tags only on change-class kinds attributed to the claimed session or user, window end a monotonic duration (Task 32); scored-service parent-child, `auth_event`, egress and honeytoken rules ignore tags. Risk re-rated Medium until built.

Sections: Wire protocol (fact `work_window`), Execution engine (Tagging and adoption), Rule format (rule D1), Risks. Quotes: "While a window is open the emit path stamps its `tag` on every event the host emits"; "never exempts anything the rules do not already exempt for tagged events"; "Rules exempt tagged events instead of guessing from process names"; D1 `- not: { tag: { present: true } }`; risk row "A claimed work window hides attacker activity | Low".

Problem. The "never exempts" sentence is circular, because the one tag condition exempts everything tagged and the supervisor tags everything. While `phylax claim` is open, a webshell spawning a shell on that host raises no D1 alert. The design never says how the agent decides an event belongs to a plan step. The window `until` is checked against the host clock and the adversary list includes "move system clocks". W1 builds `internal/agent/window.go` and the `work_window` effect, so this must be settled for W1.

Options. (a) Plan tags are stamped only on events whose process descends from the step's own child; work-window tags only on change-class kinds (`file_change`, config, account events) attributed to the claimed session or user; scored-service parent-child rules, `auth_event`, egress and honeytoken rules ignore the tag; the window end is a monotonic duration, not a wall-clock time. (b) Keep as is and re-rate the risk.

Recommended: (a); re-rate the risk to Medium until built. The authentication of `claim` itself is a W10 item (L59).

### R7. Restoring twice from the same snapshot does not raise the epoch enough

**Decided 2026-11-06:** option (a). `hello` carries the agent's highest accepted epoch; restore uses `max(snapshot, reported)+1`, and signing waits until every enrolled agent has reported. W12 Task 12a.

Section: Controller recovery. Quotes: "The restored controller raises the epoch, so agents accept steps in the higher epoch" and "The epoch rises only when the controller is restored from a snapshot". Code: `internal/store/backup.go` reads `epoch` from the restored database and does `ep++`.

Problem. The snapshot holds epoch E, so every restore from it produces E+1. After a second failure and a second restore from the same or an older snapshot, agents that accepted `(E+1, s)` from the first restored controller reject everything from the second. `hello` carries no epoch, so the controller cannot see the true maximum. W12 Tasks 12 and 13 build the restore path.

Options. (a) `hello` carries the agent's highest accepted epoch and the restored controller uses `max(snapshot epoch, all reported)+1`. (b) The operator passes `-restore-epoch` by hand. (c) Accept: restore twice from one snapshot is unlikely.

Recommended: (a). It is a one-field wire change and one `max` in `Restore`. Add the field to the `hello` row in Messages.

### R8. Signing stays locked after a controller restart, and nothing says so

**Decided 2026-11-06:** option (a). A locked controller raises a critical `controller.locked` alarm and an Overview LOCKED banner; the dead-man is unchanged. W12 Task 13a (one flag also drives the snapshot writer's skipped state).

Sections: Controller recovery (Restart safety), Trust model, Execution engine. Quote: "Plan signing and secret access stay locked until the passphrase is entered."

Problem. After a crash or reboot with nobody at the console, auto plans, facts, `deadman_confirm` and safe-mode toggles stop. In-flight dead-man timers then fire and roll back applied changes. Nothing surfaces the locked state (no Overview banner, no `notify`); T18 only checks that a plan resumes after unlock. W12's snapshot writer also waits for the passphrase ("It does nothing while pass is empty").

Options. (a) A locked controller raises a critical `notify` alarm and an Overview "LOCKED" banner; keep the dead-man as is (fail-safe). (b) Also stretch the dead-man while the controller reports locked. (c) Do nothing.

Recommended: (a). (b) weakens the safety net. Add a W12 task or a line in Task 13 so the banner and the snapshot-skipped state use one flag.

### R9. Unbounded controller disk, and audit-before-handler turns "disk full" into a locked UI

**Decided 2026-11-06:** option (a) with hard quotas: refuse bulk at 90% disk, evidence at 95%, accept only high and critical events at 98%; alerts never shed; safe mode and the kill switch exempt from the audit-write refusal. W1 Task 8b; reported by the W14 bench (`quota_level`, `skipped_events`). T83.

Sections: Event store and vault (Storage), Execution engine (Audit trail), Framing. Quotes: "indefinite for the event ... warns at 70% and 85%"; "a request is refused if the audit write fails"; alert evidence "capped at 8 MiB per item and 64 MiB per alert".

Problem. Nothing happens at 100%. Evidence has no controller-side quota, so a flooding agent can write hundreds of MB per minute. When SQLite cannot write, audited requests are refused, including safe mode, the one control needed to stop the flood, and the controller stops acknowledging events. The Invitational collects far more data than a normal run, and W14's bench reports store growth.

Options. (a) A hard evidence quota with a shed order (bulk transcripts, then flows, never alerts); the audit write for safe mode and the kill switch is exempt from the refusal; define behaviour at 95% and 100%. (b) Only the exemption. (c) Operator discipline.

Recommended: (a) with thresholds in the design (suggest refuse bulk at 90%, evidence at 95%, ingest of high and critical only at 98%). Also covers the `backup` quota point (L61).

### R10. The persistence rule cannot hold for most module tables

**Decided 2026-11-06:** option (a). Every table row must be reproducible from the module's own events plus its content files; operator actions are typed command events the module emits through `Host.Emit`; each module section lists them (13 new kinds in the kind table). Contract text, conformance check 11 and W1 Task 36 (`tables_replay`) updated.

Sections: The module contract (persistence), `checks`, `scorer`, `traceback`, `honeytokens`, `report`, `depot`, `backup`, `integrity`, `hunt`. Quote: "A table is therefore always a projection of the module's own event stream, and rebuilding it is a replay; no analyser, handler or other goroutine writes it."

Problem. Many tables hold data no event of that module carries: operator decisions (`integrity` `ledger_accept`, `hunt` `hunt_finding` state), check edits and retire in `checks`, the `scorer_item` raw samples, `traceback` baseline acceptance, `honeytoken` paths and accounts (the event carries "ids and kinds only"), `report_drafts` text, `depot_entry`, the `backup` golden tag. Re-emitting `hunt.finding` for a state change retriggers `detect`, `creds`, `report`, `backup`. The conformance replay test (W1) fails for these modules, and W8 will say "tables are projections of own events".

Options. (a) Add a rule: every table row must be reproducible from the module's own events plus its content files; operator actions are typed "command" events the module emits itself through `Host.Emit` (for example `checks.edited`, `integrity.accepted`, `hunt.decision`, `traceback.baseline_accepted`, `backup.tagged`, `report.edited`), and each module section lists which event carries each mutation. (b) Allow a second writer path for operator input tables. (c) Weaken the replay test to "rebuildable or marked non-replayable".

Recommended: (a). One rule, no new mechanism, and W1's conformance replay stays meaningful. Add the per-module event lists in the module-section pass (they are mechanical once the rule exists: the kind-table rows follow the same pass).

### R11. YAML blocks do not map one-to-one onto the Go structs

**Decided 2026-11-06:** option (b). One small type, `module.Duration`, unmarshals "90s" and "2m" in YAML and JSON and is the only exception to the one-to-one mapping; examples stay readable. Contract text and W1 Task 33 (type, schema mapping, tests).

Section: The module contract item 2. Quote: "The YAML maps one to one onto the struct (nested structs allowed, no translation layer)."

Problem. Examples in the module sections do not match their structs: `respond` `tier0.{max_per_host_per_min, breaker_window: 2m, loop:{count,window:10m}, block:{expires_after:4h}}` against `Tier0Settings{MaxPerHostPerMin, BreakerWindowSec, LoopCount, LoopWindowSec, BlockExpiresSec, Allowed}`; `content_guard` `promote`/`loop` blocks; `ad` `recycle_bin:{enable}`; `hunt` YAML keys that `HuntSettings` lacks; `firewall` `deadman: 90s` against a `time.Duration` (JSON has no duration form). W1 generates the YAML schema from the struct (CI), so the rule must exist before the first module is registered.

Options. (a) YAML keys equal JSON tags; durations are integer `_sec` fields; manifest CI generates the schema from the struct; every module example is rewritten to match. (b) Allow a typed duration wrapper that unmarshals `"90s"`. (c) Allow a translation layer.

Recommended: (a) for W1, and rewrite examples as each module is retrofitted. (b) is acceptable if you prefer readable YAML; it is one small type, but it must be the only exception.

### R12. The auto-plan path: where the probe runs, when `deadman_confirm` is sent, and what "touches a scored service" means

**Decided 2026-11-06:** all four. Probe inside each node that touches a scored service, `deadman_confirm` only after the after-probe passes; plans touching a scored service default to `rollback_plan` (lint `SS011`); "touches" is a `Touches` hit on a manifest-scored service (manifest `health:` block until discovery), one probe per host and phase; over the 8-step cap the agent answers `busy` (retry). Sample plan fixed. W1 Tasks 26, 27, 27b, 27c; T87.

Sections: Execution engine (Plans, Plan options, Dead-man switch, Plan/approve/apply, scorer-mimic probe, Auto conditions, The action contract). Quotes: sample plan `verify: { action: health.check ... needs: [reload, fw_enf] ... }` with `on_failure: stop_dependents`; "Only `rollback_plan` plans give their nodes the rollback window that makes agents keep rollback data"; "A failed after-probe rolls the node back" (Auto condition 4); "Each node that touches a learned service" against "Every node that touches a scored service" (Auto condition 3); "The executor runs steps off the receive loop (8 at once; excess is answered `failed`)".

Problem. (1) In the reference plan the probe is a separate node under the default policy: a red `health.check` rolls back nothing, and earlier nodes have already dropped their rollback data. (2) The order of `deadman_confirm` and the after-probe is unstated; confirm first means a scored-path break with the link up is only undone by the controller, probe first may exceed the 90 s default. The dead-man proves the agent link, not the scored path. (3) "Learned" and "scored" are used interchangeably; before check discovery finishes a manifest-scored service is not learned, and it is unclear whether a before/after probe wraps every node or only nodes whose `Touches` is non-empty (a 20-node pack could mean 40 probes). (4) A valid step over the 8 cap is answered `failed`, which triggers `on_failure`, including whole-plan rollback on an `auto` plan. W1 builds the controller executor and `RunAuto`.

Options. Run the before/after probe inside the node and send `deadman_confirm` only after the after-probe passes; the standalone `health.check` node is for reporting. Every plan that touches a scored service defaults to `rollback_plan`. A node is probed when its `Touches` hits a manifest-scored service, using the manifest `health:` block until discovery catches up; one probe per host and phase for nodes sharing a lock set. The controller holds per-host in-flight steps below the agent cap and the agent answers `busy` (retry), not `failed`.

Recommended: all four, and fix the sample plan. They are small and decide W1's executor tests.

### R13. Approval classes: keep four, or fold `auto_readonly` and `standing` into `auto`

**Decided 2026-11-06:** keep four approval classes; no change.

Sections: Configuration, Execution engine (approval classes, gates), Tiers, Complexity register. The classes are `click`, `auto_readonly`, `standing`, `auto`; gates `approval`, `manual`, `auto`; switches `enabled`, `act_enabled`, safe mode, `override_mode`, per-rule `mode`, per-template `auto` allowlist, content-guard shadow period.

Problem. The core reviewer counts about seven independent switches a reader must combine, which cuts against the "fewer mechanisms" preference, and proposes folding `auto_readonly` and `standing` into `auto`. W1 builds all four classes (Host methods `RunReadOnly`, `RunStanding`, `RunAuto`, the Approvals page).

Options. (a) Fold now (removes `StandingApproval`, the Approvals page and `Host.RunStanding` from W1). (b) Build as designed, revisit after the Invitational data.

Recommended: (b). `auto_readonly` exists so read-only collection plans (the service doctor, evidence runs) run while `act_enabled` is false, which is the observe-mode case; folding it into `auto` removes that. `standing` could fold into `auto_readonly` only for read-only backup nodes, and a scored-database dump is not read-only. The saving is small against W1's schedule and the risk is a redesign of the observe-mode path. If you want the fold, do it for `standing` only, before W1 Task on approval classes starts.

## Decisions needed later

Format: id, section and quote where short, options, recommendation. Items are grouped by the workstream that builds them. Cross-cutting items are decided before W3.

### Cross-cutting (before W3)

**L1. The per-module token bucket is not priority-aware.** Sections: `ModuleSpec.Rate`, `Budget.EventsPerSec`; `net` (budget 200/s covers `listener`, `net.egress_denied` and bulk `conn`), `logs` (300/s covers `auth_event` and `logs.line`), `integrity` (2/s), `winevt` ("excess is dropped and reported"). One scan or first sweep can fill the bucket and drop the `log_cleared`, `listener` or failed-login burst. Only `capture` has per-class buckets. Options: priority-aware shedding in the supervisor (reserved tokens for critical and high, bulk shed first; `detect.alert` exempt) or per-module class buckets. Recommended: the supervisor change, once.

**L2. One connection is reported by up to four producers with no dedupe.** Section: Event kinds (`conn` emitters `audit`, `winevt`, `net`, `capture`). `count`, `sequence`, `jitter` windows, `deps`, `chains` and `traceback` double-count. Options: a canonical key `(host, community_id or 5-tuple, op, start)` with stated precedence (`net`, then `audit`, then `capture`) and rules count the deduped stream; or consumers filter on `source`. Recommended: the canonical key, stated once under the event table (merges the core and module-a findings).

**L3. Analyser re-runs have no idempotency rule.** Section: Controller modules and analysers (`Every time.Duration`); `chains` re-emits `chains.chain` with grown hops; no deterministic id. Options: every analyser-emitted event carries a deterministic id (kind plus input hash; `chain` id = hash(seed kind, seed ref)) and the store drops duplicates; or a watermark per analyser. Recommended: deterministic ids.

**L4. Facts derived from agent data steer other hosts' automation.** Sections: Wire protocol (fact subtypes), Trust model. A compromised `check_runner` (the DC, the controller workstation, the Kali) can feed `scorer_probe_result` `ok: false` to open `respond`'s breaker on other hosts, or move quiet windows with `round_clock`, and the controller signs the result as a fact. Options: require corroboration (two runners, or the controller's own probe) before a breaker opens; do not make the DC a runner by default; add a Trust-model line. Recommended: both.

**L5. The operator UI has no brute-force or transport protection stated.** Section: UI shell ("`127.0.0.1` only ... One login (argon2id ...)"). One shared password also unlocks signing, and the adversary can "reach any local process on the controller host that is not ours". Options: pinned self-signed TLS on the loopback listener plus exponential login backoff; or also a console passphrase prompt. Recommended: TLS plus backoff; keep the passphrase in the UI.

**L6. Locks are released between nodes, so rollback data can go stale.** Section: Execution engine (Locks). If tier 0 or a hand change alters a resource while a plan waits at a gate, a later `rollback_plan` restores the older state over the newer one.
